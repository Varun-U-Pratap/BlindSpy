# BlindSpy — Project Plan

BlindSpy trains classifiers that tell what kind of encrypted traffic a connection carries, and whether it runs through a VPN, using only timing statistics. Every run is logged, so the report can show how each change moved the scores.

## Goal and scope

Encryption hides packet contents, so the old method of reading packets (deep packet inspection) no longer works. Apps still leave a timing pattern: voice calls send small packets at a steady rhythm, streaming downloads in bursts, file transfers run flat out. We train models on those patterns, never on the contents.

**Data:** the ISCXVPN2016 dataset from the University of New Brunswick. Each row is one connection (a "flow") described by 23 timing features, with a label. It comes in four versions, built with 15 s, 30 s, 60 s and 120 s flow timeouts. A timeout is a setting used when building flows: it decides when an inactive flow is closed. It is not each flow's duration.

**Three tasks**, matching the 2016 paper (Draper-Gil et al., ICISSP), each scored on its own:

| Task | What it is | How it is scored | Data folder |
| --- | --- | --- | --- |
| A1 | One binary classifier: VPN vs non-VPN | VPN and non-VPN precision and recall; macro F1; ROC-AUC | `Scenario A1-ARFF` (names corrected by COLUMN_MAP; 120 s flowPktsPerSecond restored from B 120 s) |
| A2 | **Two separate 7-class classifiers**, one on VPN flows and one on non-VPN flows (A2 files hold total_fiat/total_biat in place of std_fiat/std_biat) | Each model scored separately. Never merged into one 14-class score | `Scenario A2-ARFF` |
| B | One 14-class classifier over VPN and non-VPN traffic together | Macro F1 and per-class scores over all 14 labels | `Scenario B-ARFF` (names corrected by COLUMN_MAP) |

**Comparing with the paper:** the paper reports precision and recall per class, using Weka's C4.5 and KNN with 10-fold cross-validation. We compare precision with precision and recall with recall, under a matched protocol (see Metrics), never the paper's precision against our F1. scikit-learn's decision tree is a close substitute for C4.5, not an exact copy, so the report calls it a *baseline approximation*.

**What BlindSpy can and cannot claim**

- It predicts traffic type from aggregate timing statistics and never reads packet contents.
- It does not prove that traffic is encrypted.
- The data was captured in 2016 in a lab, with specific apps and one VPN setup. Results may not hold for today's apps, VPN providers or networks. The introduction and conclusion both say so.

**Deliverables**

- Jupyter notebooks covering loading, exploration, training and evaluation.
- One final trained model per task, plus `predict.py`. It checks the feature names, order and units of its input and rejects bad files rather than guessing.
- A report that shows the history: every experiment, what changed, the scores, training time and graphs.
- The history itself: `EXPERIMENT_LOG.md`, `DATA_CHANGELOG.md`, `reports/history.csv`, and zips of `mlruns/` and `data/processed/` at each milestone tag.
- The Streamlit demo and a short video of it.

**Success conditions**

- **Reproduction:** results comparable to the paper's under a documented, matched protocol.
- **Improvement:** a better score than our own baseline under the same protocol. Beating the paper is a goal, not a guarantee.
- **Robustness:** check whether the gain holds under session-aware evaluation, where the data allows it.
- **Practicality:** prediction time and model size reported next to the scores.
- Every reported number traces to a config file, an MLflow run and a git commit.

**Out of scope for the core plan:** extracting new features from the raw packet captures and deep learning on packets. Both sit under Stretch goals.

**How it stays extensible**

- **Raw data is never edited.** `prepare_data.py` writes each cleaned version to its own folder, `data/processed/<data_version>/`, and updates `data/manifest.json`. The manifest records the source URL, each file's hash, row counts, the verified column map, feature names, label counts, the cleaning rules applied and the data version.
- **New model** → add one function to the registry in `models.py`. It returns a full scikit-learn `Pipeline` (preprocessing + model), so a model and its preprocessing always travel together. Training and evaluation code stay untouched.
- **New task or timeout** → a config field (`task: A1`, `timeout: 15`), not new code.
- **New features later** (for example from the raw captures) → a new loader in `data.py` that outputs the same table shape. Everything downstream works unchanged.
- **One fixed test split per task and data version**, saved once inside that version's folder and reused by every run. All runs on the same data version are scored on the same rows, so their scores are directly comparable.
- **Notebooks read results; they don't create them.** Training goes through `run_experiment.py`, so a run never depends on the order notebook cells were run.

## Tracking and history

History is kept at four levels that link to each other. Git records what code changed, MLflow records what each run measured, the experiment log records why we tried it and what we learned, and data versions record how the cleaned data changed. Every MLflow run stores the git commit and the experiment ID, so any number in the report traces back to its code.

**Runners: one official history, optional personal tracks**

- A **runner** is the person whose laptop runs an experiment. Each runner has a folder named by their GitHub username. The **official runner is ****`utsav-s-r`**: official experiments run only on that laptop, so the history is one continuous record and all timings come from the same hardware.
- Per-runner folders: MLflow store `mlruns/<runner>/` (an SQLite database mlruns/<runner>/mlflow.db for run records plus mlruns/<runner>/artifacts/ for plots and models; SQLite is MLflow's current default, the old folder store is being retired; MLflow stays at the locked version until hand-in) (git-ignored, zipped to backups/) and experiment notes `reports/experiments/<runner>/E##.md` (committed). The runner name comes from `runner:` in a git-ignored `configs/local.yaml` on each laptop; `run_experiment.py` refuses to run without it.
- Anyone else may keep a full personal track from start to finish in their own folders. It never mixes with the official one. The report is built only from `utsav-s-r`; another track may be cited as an independent replication.
- **Shared by everyone, never per runner:** the code, configs, data versions (`data/processed/vN/`, identical everywhere because the script is deterministic) and `models/final/` (official only).
- Every MLflow run is tagged with `runner` and `machine` (OS, CPU model, RAM), so a run's origin is never in doubt.

**Level 1: Git (code history)**

- `main` always works. Each piece of work gets a branch (`exp/E07-xgboost-tuning`, `feat/data-loader`) and is merged into the dev branch. No pull requests: Varun merges dev into main when he wants.
- Commit messages start with the experiment ID when they belong to one: `E07: add XGBoost to model registry`.
- A git tag marks each milestone (`v0.1-baseline`, `v0.2-tuned`, `v1.0-final`). Tags go on the dev commit the results came from and are pushed. They are for traceability (anyone, or any tool, can check out exactly the code behind a result); nobody has to read them.

**Level 2: MLflow (every run, automatically)**

| Kind | What is recorded |

One file per experiment: reports/experiments/<runner>/E##.md. **Level 4: Data versions (every cleaned version is kept)**

Cleaning changes are history too: the column-name fix or a new odd-value rule can move every score. So data is versioned the same way models are.

- **Version number:** `data_version` in `configs/base.yaml` and `data/manifest.json`, starting at `v1`. Increase it whenever anything that changes the cleaned output changes: a cleaning rule, the column map, the parser, row filtering or the split seed.
- **Kept snapshots:** `prepare_data.py --version v2` writes to `data/processed/v2/` and refuses to overwrite an existing version folder. Each folder holds the Parquet file for every task × timeout, the `splits/` JSON files (splits belong to a data version, because cleaning can change the rows) and a copy of that version's manifest.
- **CSV copies only for the current version:** `data/processed/csv/` is overwritten with the latest version. Any old version can be exported again with `prepare_data.py --export-csv v1`.
- **Changelog:** `reports/DATA_CHANGELOG.md`, newest first, one entry per version: version, date, author, what changed, why, rows and files affected, and the git commit. Example: `v2 — corrected column names after the column-name check; all 20 files; no rows dropped`.
- **Logged per run:** every MLflow run logs `data_version` and the data hash, so the run table can be filtered with "data v1 vs v2".
- **In the report:** when a data version changes, rerun the current best model on the new version and log it as its own experiment, so the effect of the cleaning change is measured. The Dataset section includes the changelog as a table.
- **Storage:** about 15–25 MB of Parquet per version (v1: 18.7 MB). `data/processed/` stays git-ignored and is zipped with `mlruns/` into backups/ at each milestone tag.

**Storage: keep every model.** Every official run keeps its metrics, plots and its trained model file, so every intermediate model exists and can be reloaded by run ID. Models are saved with joblib compression level 3 (lossless: the model reloads identically; a 300-tree Random Forest on B 15 s is 22.4 MB instead of 171.9 MB), which keeps the whole store at about 2–3 GB. The only exception is Optuna trials: they keep settings and scores, and the best trial is retrained and saved (config flag `save_model`: true by default, false only for Optuna trials). If the projected total of `mlruns/` goes above 20 GB, the team is told. `mlruns/` is git-ignored and zipped to backups/ at milestones; the final models are committed to `models/final/`.

**Turning history into the report:** `export_history.py` writes every run to `reports/history.csv` and draws the progress charts. The report never needs numbers copied by hand.

## Metrics and report graphs

The main score is **macro F1 on the held-out test set**. Accuracy alone misleads here: some classes have many more flows than others, so a model can score high accuracy while failing the small classes.

**Evaluation protocol (leakage-safe)**

1. Split each dataset once: 70% train, 15% validation, 15% test, keeping class proportions equal in each part, with seed 42. The test set is never used for tuning or model choice. Only E13 and E14 use other seeds (42–51), on purpose, to measure stability; they never touch the seed-42 test rows.
2. Choose settings with 5-fold cross-validation **inside the training set only**.
3. Compare candidate models on the validation set, then pick the final configuration (the highest validation macro F1). A comparison set fixed before the test set is opened (the best validation variant of each method type per task) is also scored, as comparison only; it never changes the final configuration.
4. Retrain that configuration on train + validation and score it **once** on the test set (each comparison-set model the same way, once), at the `v1.0-final` tag.
5. Scaling, imputation and resampling (SMOTE and others) run inside the scikit-learn pipeline, so they are fitted within each training fold. Never resample the whole dataset before splitting.
6. **Paper benchmark, kept separate:** to compare with the paper, also run its own protocol (10-fold cross-validation on the full file) and report it in its own table. Our 70/15/15 results are not the same as the paper's protocol.
7. **Session-aware check:** related flows from one recording session can land on both sides of a random split and inflate scores. If the ARFF files identify the session, also run a group-aware split that keeps each session on one side (E11). If they don't, the report lists this as a limitation.

**Metrics**

| Metric | Why it is included |
| --- | --- |
| Macro F1 (main) | Treats every class equally, so small classes count |
| Precision and recall per class | Compared with the paper's own precision and recall figures |
| Weighted F1, accuracy, balanced accuracy | Comparable with other studies |
| Confusion matrix | Shows which classes get mixed up (for example CHAT vs BROWSING) |
| ROC-AUC (A1 only) | Shows how well the model separates VPN from non-VPN at any threshold |
| Cross-validation standard deviation | Shows whether a gain is real or noise |
| Bootstrap 95% confidence intervals on final test scores | Tells whether two close models really differ |
| Training time, prediction time per 1,000 flows, model size | Practical cost; the paper also reports speed |

**Also measured and recorded** (from how the related papers report results):

- **Dataset summary** per data version and task: initial rows, duplicates removed, conflicting duplicates, final rows, missing values, features kept, number of classes, largest-to-smallest class ratio (for example 12.38:1), train / validation / test sizes.
- **Macro F1 vs weighted F1, and the gap between them:** a large gap means small classes are doing worse.
- **Best and worst class** by F1 and by recall, named with their values.
- **Top 5 confusion pairs** by count (for example "VPN-BROWSING predicted as BROWSING: 80 flows"), generated automatically from each confusion matrix.
- **Generalisation gap:** cross-validation mean minus validation (or test) score.
- **Search size** for every tuning run: configurations or trials, total fits, best CV score, search time.
- **Calibration:** ECE and a reliability diagram for the final models (E15).
- **Stability across split seeds:** mean ± std over 10 seeds (E14).
- **Learning curve:** score against training-set size (E13).
- **Model complexity:** number of trees, mean tree depth and number of nodes for tree models; support-vector count for SVM.

**Graphs for the report** (made by `export_history.py` and the final notebook)

1. **Progress chart:** best macro F1 per task over experiments E01→En, with our baseline marked and a vertical line wherever the data version changed. This is the main "we improved it" picture.
2. **Paper vs ours:** per-class precision and recall under the matched 10-fold protocol.
3. **Model comparison:** macro F1 per model per task, with cross-validation error bars.
4. **Accuracy vs cost:** macro F1 against training time, one dot per run.
5. **Timeout effect:** macro F1 and balanced accuracy at 15, 30, 60 and 120 s per task, with each version's class mix shown beside it. If the mix differs a lot, the report says the comparison is confounded instead of claiming that one timeout causes better scores. The 60 s files also differ in what VOIP and FT flows look like (E00), so a 60 s result that breaks the trend is not read as a timeout effect.
6. **Feature-group ablation:** macro F1 using all features vs each feature group alone (E09).
7. Confusion matrices for the final models, normalised.
8. SHAP summary and feature importance. Because many features are correlated, these describe how the model behaves, not what causes the traffic patterns. Includes 3–4 worked examples: one flow each, with its prediction, confidence and the features that drove it most.
9. Class and feature distributions from the exploration notebook, plus a data-funnel chart per data version (rows remaining after each cleaning step, by class).
10. Optuna tuning history: the score at each trial. Also: the learning curve (E13), a seed-stability box plot (E14), a reliability diagram per final model (E15), and the top-5 confusion-pair table per task.

## Roadmap

The first goal is one complete, tracked run (A1 at 15 s) before anything else is expanded, so the hardest connections between parts get tested early. Sound evaluation and the report always come first.

Report writing runs in parallel from the start (see *Team rules*) and finishes after the final model. Stretch goals start only after v1.0-final.

**Expansion order:** A1 at 15 s → all tasks at 15 s → all timeouts for the baselines → tuned models per task → session-aware check, learning curve, seed stability and calibration. All of these are required, none optional.

A phase is finished when its **Done when** check passes. Each task names the file it produces, so anyone can pick up where someone else stopped.

### Phase 3 — Improve → tag `v0.2-tuned`

Each experiment changes one thing against the current best, so the log shows what caused each gain. Every experiment may fail as well as succeed; a failure is logged the same way. Run first at 15 s for all tasks; repeat at other timeouts only for the winners. Winner: a model whose 15 s validation macro F1 beats that task's current best by at least 0.03 (above the largest Phase 2 CV std, 0.025); only winners are rerun at 30, 60 and 120 s. The 0.03 is written into each experiment file before running. Why: a gain smaller than the CV spread could be noise from the split, so only a margin above it counts as a real improvement. A fixed number, set before running, keeps the choice honest and repeatable, and keeps the 'one change, then confirm' protocol. Not chosen: always rerunning the top 2 per task (spends runs on models that did not beat the tree) or running everything at every timeout (about 4× the runs and storage, and it drops the screen-then-confirm design).

**Rules for Phase 3 (the reason follows each rule):**

- **Setup commit first.** `model_compress: 3` in `configs/base.yaml` (logged as a param; a test checks that a compressed model reloads and predicts identically) and `uv add xgboost lightgbm optuna imbalanced-learn` go in ONE commit, pushed before any Phase 3 run, so every Phase 3 run has the same uv.lock hash. Adding them leaves scikit-learn, numpy, pandas, scipy, joblib and mlflow at their locked versions (adds xgboost 3.4.1, lightgbm 4.7.0, optuna 5.0.0, imbalanced-learn 0.14.2). After the commit, rerun one Phase 2 baseline in a scratch clone with its own MLflow store (so the official result tables are not changed) and confirm identical scores.
- **Order:** setup → E04 → E05 → E06 → E07 → E08 → E10 → E17 (equal tuning budget) → choose final configs and the comparison set → E09, E13, E14 on the final configs → E11 note → E16 → notebooks and report → storage check → tag → verification at the tag. Winner reruns at 30, 60 and 120 s happen as soon as the rule fires. E09, E13 and E14 describe the chosen model, so it must exist first. The Phase 3 checklist below is in this order.
- **Threads:** n_jobs=1 inside every model (XGBoost and LightGBM threads = 1); the 5 CV folds stay parallel as in Phase 2; logged as a param. Optuna trials run one at a time. Why: training times stay comparable with Phase 2, results are deterministic, and parallel TPE trials are not reproducible even with seed 42.
- **Peak memory:** keep tracemalloc (comparable with Phase 2) and also log the peak RSS of a fit in a fresh child process (resource.getrusage; ru_maxrss is bytes on macOS, kilobytes on Linux) minus the child's RSS just before the fit. Why: tracemalloc cannot see the C++ memory XGBoost and LightGBM use.
- **Model size:** log both the uncompressed size (as in Phase 2) and the compressed file size, so Phase 2 and Phase 3 sizes stay comparable.
- **Current best and reruns:** the current best is the highest 15 s validation macro F1, whatever the margin; later experiments build on it. The 0.03 margin only decides reruns at 30, 60 and 120 s. A winner is rerun there with its 15 s settings (tuned hyperparameters and balancing included); nothing is re-tuned per timeout, because that would be a different, 4× costlier experiment and would break the screen-then-confirm design.
- **E07 scope:** the best 2 of Random Forest / XGBoost / LightGBM are picked per task by 15 s validation macro F1 (each task's best family gets tuned), plus KNN. Trials keep settings and scores only; the best trial is retrained and saved. Trial runs are tagged and kept out of the result tables.
- **E08:** XGBoost has no class_weight, so its balanced step uses sample_weight from compute_sample_weight("balanced"). SMOTE with k_neighbors=5 is safe: the smallest training class is 53 rows (MAIL, A2-NonVPN 30 s), about 42 per CV training fold.
- **E09 is analysis only.** If a feature set beats the best by ≥ 0.03, stop and ask the team. Why: picking features from validation scores risks overfitting the choice.
- **E10:** both steps train only on B training rows; step 1's label (VPN / non-VPN) comes from the B label. Never the A1 split: A1 and B hold the same flows with different splits, so an A1-trained model has seen B validation flows.
- **E16 data:** built by a committed script into `data/processed/kaggle/k1/` with its own manifest, hashes and DATA_CHANGELOG entry; logged as data_version kaggle-k1; data v1 untouched. (c) = the best task-B model type and hyperparameters retrained on the Kaggle rows under protocol (b), because the Kaggle CSV is in the A2 layout (total_fiat / total_biat) and our B models use std_fiat / std_biat.
- **E17 equal tuning budget**, before the final choice: every method type gets the same 50-trial Optuna search per task as E07 (TPESampler seed 42, 5-fold CV macro F1 on train, trials one at a time): decision tree, logistic regression and SVM-RBF in all 4 tasks, Random Forest in A2-VPN, A2-NonVPN and B, LightGBM in A1 = 16 searches. Search ranges written into E17.md and the configs before running. Why: otherwise a per-type comparison mixes tuned and untuned models (the weakness we cite for Isnan et al.). Balancing (E08) stays only on the models it was run on; the comparison table shows each model's balancing.
- **Final config per task:** model AND timeout together, from runs that exist, by the highest validation macro F1 among all model-selection runs (any experiment incl. E17, any timeout); written to `configs/final/<task>.yaml` with the reason, together with the comparison set. Only fallback: a model whose saved file is over 50 MB (GitHub warning) is replaced by the next best that fits. Why: the measured CV spread of the candidate models is 0.004–0.006 (the four headline models' CV standard deviations are 0.0028–0.0058), far below 0.03, and the goal is the best score on unseen traffic. This deviates from the tie rule set before Phase 3 (a gap under 0.03 counted as a tie, broken by the simpler model), which would have picked KNN or Random Forest 0.015–0.029 below the best. The deviation is reported openly in the E files and report section 3, and the old rule's picks (computed by code over all runs, results.old_rule_choice) are scored once on the test set too, to show what it would have cost: as comparison-set members where they are members, otherwise as extra configs in configs/final/old_rule/ (A1 and A2-VPN: the E04 signed-log KNN, k = 5).
- **Comparison set for Phase 4:** per task, the best 15 s validation variant of each method type (tree, KNN, logistic regression, SVM, Random Forest, XGBoost, LightGBM) = 28 models (a type's variants are its default, tuned and balanced runs; KNN includes the E03/E04 preprocessings; the E10 two-step counts as XGBoost; the E01 majority baseline stays a reference, not a member), written to configs/final/ together with the 4 headline models before the test set is opened. Safeguards: nothing is chosen, swapped or re-tuned after test scores are seen; the headline per task is fixed beforehand; a difference between two models is tested with a paired bootstrap on the same test rows with Holm correction for the number of comparisons, otherwise only described; scope stated (15 s, one 70/15/15 split, seed stability E14 only for the headline models). SHAP, calibration (E15), E09, E13 and E14 stay on the 4 headline models. Only the 4 headline models are saved to models/final/ (committed); comparison-set and old-rule models stay as MLflow artifacts, so the 50 MB file limit applies only to the headline models (the E07 LightGBM for B in the comparison set is 62.5 MiB).

E08 runs on the current best per task after E07, which may still be the untuned E02 tree if nothing beat it. E10 uses the current best B model type and hyperparameters for all its models (the direct 14-class model, the VPN / non-VPN step and both 7-class models), so the only change is the structure.

Phase 4 (retrain on train + validation, save, predict.py, SHAP, calibration, demo) must support whatever pipeline is chosen, including a two-step or imblearn pipeline if one wins.

## Team rules, risks and stretch goals

**Team rules**

1. Before starting an experiment, claim the next ID by creating its file in reports/experiments/<runner>/ instead of editing `EXPERIMENT_LOG.md`, so two people never pick the same number.
2. Train only through `run_experiment.py` with a committed config. Official runs must come from code that is committed AND pushed to GitHub, so anyone can look up the exact code behind a result. run_experiment.py checks this before training: if there are uncommitted changes, or the current commit isn't on GitHub yet, it stops and prints exactly what to do (for example: commit, then git push origin dev, then run again). Runs in personal tracks only get a warning. The check is covered by a test, and the message is shown in the README.
3. Change one thing per experiment. When the score moves, we know why.
4. Every random step uses seed 42: the split, `random_state` of every model (tree, Random Forest, XGBoost, LightGBM), the Optuna sampler (`TPESampler(seed=42)`), SMOTE and random oversampling, and the bootstrap. A rerun of any config must reproduce its scores exactly. The only exceptions are E13 and E14, which deliberately use seeds 42–51 to measure stability.
5. Official experiments run only on the official runner's laptop (`utsav-s-r`). Others write code and configs, test locally, and may keep a personal track in their own folders.
6. Never tune on the test set. Score it only once, at the v1.0-final tag (each final and comparison-set model once; nothing is chosen, swapped or re-tuned after test scores are seen).
7. Write the log entry the same day, including failures. Ideas that didn't work are part of the story and show real effort.
8. Each experiment file states its hypothesis and a numeric pass/fail threshold **before** running, for example "H: Random Forest beats the best baseline's validation macro F1 by at least 2 points". The result section then says supported or not supported. A pre-stated threshold can't be moved after seeing the result.
9. Any change that alters the cleaned data creates a new data version: new folder, `DATA_CHANGELOG.md` entry, and a rerun of the current best model under the next free experiment ID. Never edit a version folder in place.
10. Commit notebooks with outputs stripped. Charts for the report go to `reports/figures/`.
11. A short sync every 2–3 days: read the newest log entries and pick the next experiments.

**Risks**

| Risk | Effect | Fallback |
| --- | --- | --- |
| ARFF files fail to parse, or odd values have unclear meaning | Blocks everything | Fixed first in phase 0+1, with tests; every cleaning rule documented, nothing set to zero by default |
| No session information, so leakage can't be checked | Scores may look too good | State it as a limitation; report the paper's 10-fold benchmark separately |
| Our numbers don't match the paper's | Weak reproduction claim | Document every difference in protocol (C4.5 vs scikit-learn's tree, splits, cleaning) |
| Small classes (for example chat) stay weak | Lower macro F1 | Balancing ladder in E08; discuss honestly |
| Team members' results don't match | Confusing history | Shared lock file, fixed seeds, data hash logged per run |
| Phases take longer than planned | Thin report | Nothing is dropped: start independent tasks of later phases in parallel (see the role table) and check progress at every sync |
