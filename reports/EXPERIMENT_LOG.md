### E17 — Equal tuning budget for every method type (2026-10-28, utsav-s-r)

Why this experiment exists (decided 28 Oct after E10, user OK; plan item "Decided 28 Oct, after
E10"): Phase 4 scores a comparison set, the best validation variant of each of the 7 method types
per task. Up to now only some types were tuned: E07 searched XGBoost and KNN in all tasks,
LightGBM in A2-VPN, A2-NonVPN and B, and Random Forest in A1. The decision tree, logistic
regression and SVM ran with defaults only. A comparison of tuned against untuned models would
favour the tuned types for the effort they got, not for what they can do (the weakness we cite
for Isnan et al.). E17 gives every remaining type the same search E07 used, so each type enters
the comparison with the same budget.

Hypothesis: tuning helps every type, most of all logistic regression and SVM. Their E03 defaults
scored only 0.30-0.60 macro F1 because the raw timing features span six or more orders of
magnitude (E04 showed that a signed log fixes this for KNN). Even tuned, they should stay below
the gradient-boosted models, so the overall best per task does not change.

Threshold (set before running, never moved afterwards), validation macro F1 at 15 s; reference
values from `reports/phase3_tables.md` and `reports/baseline_tables.md`:
- (a) in at least 12 of the 16 searches the tuned model scores above its untuned version (E02
  tree, E03 logistic regression, E03 SVM, E05 Random Forest, E06 LightGBM);
- (b) after E17, the best run per task (highest 15 s validation macro F1 of all selection
  experiments) is still an XGBoost or LightGBM model in at least 3 of the 4 tasks;
- (c) the searches choose the signed log for logistic regression and SVM in at least 6 of the 8
  searches.
Each part gets its own verdict.

Winner rule (decided 28 Oct, written here before running): a model whose 15 s validation macro
F1 beats that task's current best by at least 0.03 is a winner and is rerun at 30, 60 and
120 s with its 15 s settings (nothing is re-tuned per timeout: that would be a different, 4
times costlier experiment). Why 0.03: it is above the largest Phase 2 CV standard deviation
(0.025), so a smaller gain could be noise from the split; a fixed number set before running
keeps the choice honest and repeatable. The current best is the highest 15 s validation macro
F1 whatever the margin; the 0.03 only decides the reruns. (The final choice per task no longer
uses the 0.03: it is the highest validation macro F1, decided 28 Oct after E10.)

Change vs the untuned runs (one change: the hyperparameters, chosen by search), 16 searches:
- decision tree, logistic regression, SVM-RBF: all 4 tasks;
- Random Forest: A2-VPN, A2-NonVPN, B (A1 was searched in E07);
- LightGBM: A1 (the other tasks were searched in E07).
Each search as E07: Optuna `TPESampler(seed=42)`, 50 trials run one after another, each trial
scored by the mean macro F1 of 5-fold stratified CV on the training rows (folds in parallel, each
model on one thread). Validation and test rows are never seen by the search. The best trial's
settings are retrained on all training rows and scored on validation like any other run and
saved; trials keep settings and scores only (nested runs tagged `trial=True`, protocol
`optuna_trial`, kept out of the result tables). The retrained run's CV mean must equal the best
trial's exactly.

Search ranges (user OK 28 Oct; written into `scripts/make_configs.py` and every
`configs/experiments/E17_<model>_<task>_15s.yaml` before running; Random Forest and LightGBM
use exactly the E07 ranges, so their searches match E07's):
- Decision tree: criterion gini or entropy; max_depth 3-40 or no limit; min_samples_leaf 1-50;
  ccp_alpha (cost-complexity pruning, the nearest scikit-learn has to C4.5 pruning)
  1e-6-1e-2 (log scale). A monotone transform such as the signed log cannot change a tree's
  splits, so it is not searched.
- Logistic regression: signed log before StandardScaler yes or no; C 1e-3-1e3 (log scale);
  max_iter fixed at 1000 as in E03; L2 penalty, lbfgs solver (scikit-learn defaults).
- SVM-RBF: signed log before StandardScaler yes or no; C 1e-2-1e3 (log scale); gamma
  1e-4-1e1 (log scale); cache_size fixed at 1000 MB (speed only, results unchanged).
- Random Forest (as E07): n_estimators 100-1000; max_depth 5-40 or no limit;
  min_samples_leaf 1-10; max_features sqrt, log2 or a fraction 0.3-1.0.
- LightGBM (as E07): n_estimators 100-1000; learning_rate 0.01-0.3 (log scale); num_leaves
  15-255; subsample 0.5-1.0 with subsample_freq fixed at 1; colsample_bytree 0.5-1.0;
  min_child_samples 1-50.
The signed log is offered to logistic regression and SVM as a choice inside the search (not as
a separate experiment like E04) because both, like KNN, depend on distances or linear scales
that the raw feature ranges distort; the search decides per task. Balancing (E08) is not part of
E17: it stays only on the models E08 ran on, and the comparison table shows each model's
balancing.

Cost check before running (throwaway fits, nothing logged): one SVM fit on the 12,651 B
training rows takes 2.2-3.9 s at the edges of the range (C 1000 with gamma 10 or 1e-4, C 0.01
with gamma 1e-4, signed log with C 1000), so no search is expected to stall.

Protocol as E07: data v1, 15 s, test set untouched. New registry option: `signed_log` for
logistic regression and SVM (`src/blindspy/models.py`); without it the pipelines are exactly the
E03 ones.

### E16 — Reproduce Isnan et al. (2026) on the Kaggle CSV, then correct it (2026-10-29, utsav-s-r)

Purpose (plan): Isnan et al. report 88.01% accuracy and 87.97% weighted F1 for a 300-tree Random
Forest on 14 ISCXVPN2016 classes. E00 found that their data, the Kaggle CSV, is the eight A2
files from all four timeouts stacked, so their duplicate removal and their 80/20 split mix
timeouts. E16 (a) reproduces their setup exactly, (b) repeats it with the timeouts kept apart,
and (c) trains our best task-B model type and settings under (b). No E16 result feeds model
selection (protocol tags are not "holdout"; E16 is not a model-selection experiment).

Data: own data version kaggle-k1 (`scripts/prepare_kaggle.py --version k1` ->
`data/processed/kaggle/k1/`, manifest copied to `data/kaggle_k1_manifest.json`; DATA_CHANGELOG
entry; data v1 untouched). Found while building it: the CSV keeps the A2 files' row order, in
the order 120, 15, 30, 60 s (NonVPN then VPN within each), so every CSV row's source file,
timeout and row number are known exactly; each block was checked against its ARFF file (all 23
features at 12 significant digits and the label). The split files keep the rows in the order
`train_test_split` returns them (not sorted), because a seeded forest's bootstrap samples and an
unshuffled 5-fold CV depend on row order, and Isnan et al. trained on that order (found in the
recheck before E16; an earlier draft sorted them). Two builds into separate folders gave identical
hashes for all 6 files. Counts (manifest): 59,706 rows, 14 labels (the B classes);
40,987 after dropping exact duplicates over the whole CSV (Isnan et al.: 40,987), split 32,789 /
8,198 (theirs: 32,789 / 8,198); 7,093 distinct rows appear in 2-4 timeout files (2,475 in 2,
1,286 in 3, 3,332 in 4), as E00 found.

Their setup, read from their paper (about/related/intechno-2026_rf-flow-classification.pdf, read
again 29 Oct): exact duplicates dropped; labels encoded with LabelEncoder (alphabetical, the same
class order as our string labels, so the stratified split is the same); stratified 80/20 split
with random_state 42; GridSearchCV with stratified 5-fold cross-validation (scikit-learn's
default, no shuffling) and accuracy as the score over n_estimators {100, 200, 300}, max_depth
{None, 20, 30}, min_samples_split {2, 5}, min_samples_leaf {1, 2} (36 configurations, 180
fits), Gini, max_features sqrt, bootstrap, random_state 42; their pick 300 trees, max_depth
None, min_samples_split 2, min_samples_leaf 1; test accuracy 88.01%, weighted F1 87.97%.

Protocols (all with seed 42; Random Forest with n_jobs = 1 per model and the grid's CV fits in
parallel, which does not change a seeded forest's result):
- (a) Isnan et al.: their dedup over the whole CSV, their split, their grid search, then the
  chosen model refitted on the 32,789 training rows and scored once on the 8,198 test rows.
- (b) Timeouts kept apart: for each timeout t, only the rows from the two A2 files of t,
  exact duplicates dropped within t, a stratified 80/20 split of those rows (seed 42), the same
  grid search, the chosen model scored on t's test rows. A flow and its copies from other
  timeouts can then never be on both sides. 4 runs (15, 30, 60, 120 s); after dedup 18,074 /
  13,638 / 14,729 / 9,589 rows.
- (c) Our model under (b): the current best task-B model type and settings (E07 XGBoost, tuned:
  `configs/final/B.yaml`, copied from E07-xgb-B-15s), retrained on each timeout's training rows
  of (b) and scored on the same test rows; no grid search (our settings are fixed). The Kaggle
  rows use the A2 column layout (total_fiat / total_biat), so the model is retrained, not reused.
  4 runs.
Reported for every run: accuracy and weighted F1 (Isnan et al.'s scores) and macro F1 (ours),
per-class precision / recall / F1 and the confusion matrix; for (a) and (b) also the grid's best
settings and best CV accuracy.

Hypothesis: (a) reproduces their numbers closely, since their setup is fully specified and seeded.
(b) scores lower than (a): in (a) the same flow can sit in the training set at one timeout and in
the test set at another (as a slightly different row, so dedup does not remove it), which helps the
model; (b) removes that. (c) scores at least as high as the Random Forest under (b), as in our own
experiments where tuned XGBoost beats the forest on task B (E05-E07).

Threshold (set before running, never moved afterwards):
- (a) test accuracy within 0.01 of 88.01% and weighted F1 within 0.01 of 87.97%;
- (b) the mean test accuracy over the 4 timeouts under (b) is at least 0.01 below (a)'s;
- (c) the mean test accuracy over the 4 timeouts under (c) is at least the mean under (b).
Each part gets its own verdict. The (a) - (b) gap is reported in any case.

Winner rule (decided 28 Oct): not applicable; E16 never feeds model selection, and its scores
are on the Kaggle rows, not on our v1 validation rows.

### E15 — Confidence calibration of the headline models, on validation (2026-10-31, utsav-s-r)

Purpose (plan, Phase 4; rules fixed in the E12 addendum item 3, 31 Oct): `predict.py` and the
demo show a confidence for every prediction, so check on the validation rows, before the test
set is opened, whether that confidence can be trusted, and decide per task whether an isotonic
calibrator is used for the reported confidence. E15 never changes the predicted class, so it
cannot change any test score of E12 except the test ECE.

What is measured (per task, the headline config `configs/final/<task>.yaml`, fitted on the
training rows only, which reproduces its source run):
- ECE: confidence = the probability the model gives its predicted class; 15 equal-width bins on
  [0, 1]; ECE = sum over bins of (rows in bin / all rows) x |accuracy in bin - mean confidence in
  bin| (`src/blindspy/calibration.py`); plus a reliability diagram (uncalibrated and isotonic).
- Calibrator: `CalibratedClassifierCV(method="isotonic", cv=5, ensemble=False)` fitted on the
  training rows only (base model fitted once on all training rows; isotonic mapping from 5-fold
  out-of-fold predictions; no validation label is used to fit it). No other method is tried.
- Calibrated confidence = the calibrated probability of the UNCALIBRATED model's predicted class
  (`calibration.predict_with_confidence`); the calibrated argmax is never used as the
  prediction. Logged as a check: how often the base model inside the calibrator predicts the
  same class as the plain fit (must be every row), and how often the calibrated argmax would
  differ (information only).
- Adoption rule (fixed 31 Oct): calibration is adopted for a task if the uncalibrated validation
  ECE is above 0.05 AND the isotonic validation ECE is lower. The decision per task is written
  below and copied into the E12 configs before the test set is opened.

Hypothesis: gradient-boosted trees with hundreds of trees fitted to the training rows are
somewhat overconfident on new rows, and the two A2 headline models were trained with class
weights (A2-VPN) or random oversampling (A2-NonVPN), which moves probability mass toward small
classes, so they are expected to be the least calibrated. Isotonic calibration, learned from
out-of-fold predictions, should lower the ECE wherever it is clearly above zero.

Threshold (set before running, never moved afterwards):
- (a) the uncalibrated validation ECE is above 0.05 in at least 2 of the 4 tasks;
- (b) the isotonic validation ECE is lower than the uncalibrated one in all 4 tasks;
- (c) calibration never changes the predicted class: in all 4 tasks the base model inside the
  calibrator predicts the same class as the plain fit on 100% of validation rows, and the plain
  fit's validation macro F1 equals the source run's (`source_val_f1_macro` in
  `configs/final/<task>.yaml`) to all digits.
Each part gets its own verdict. The adoption decision follows the fixed rule above, not (a)/(b).

Winner rule (decided 28 Oct): not applicable; E15 changes no model, setting or prediction.

Change vs the headline model: none to the model; one isotonic calibrator added on top for the
reported confidence. Configs `configs/experiments/E15_<task>_15s.yaml` (kind "calibration",
`scripts/make_configs.py`), data v1, 15 s. Every run saves the calibrated model (compression
level 3), the reliability table and diagram, and the validation predictions with both
confidences.

Validation ECE is evidence for the decision only. The final model's calibration is measured once,
on the test set, in E12 (with the probabilities actually used: calibrated where adopted, else the
original; the uncalibrated test ECE beside it).

### Correction before the runs (31 Oct 2026; user OK): shuffled calibration folds

The calibrator bullet above says `cv=5`. In scikit-learn an integer `cv` means 5-fold
`StratifiedKFold` WITHOUT shuffling, and the training rows are stored in file order
(`train.index` is increasing in all 4 tasks), so each fold holds out whole blocks of the file.
Found in the first run (pilot) `E15-A1-15s` (run a98da1299a5c44e19ba6fac8c4ed5813, commit 6281f60,
kept in MLflow and superseded): A1 validation ECE 0.0552 uncalibrated but 0.1918 "isotonic",
mean isotonic confidence 0.7391 against a validation accuracy of 0.9309. Those two A1 ECE values
are the only E15 results seen before this correction.

Root cause, measured on the TRAINING rows only (`scripts/fold_order_check.py` ->
`reports/fold_order_check.json`; no validation or test row enters any model): the out-of-fold
predictions the isotonic map learns from are much worse with unshuffled folds than with the
project's shuffled folds, so the map learns that a high confidence is wrong far more often than
it is on random-split rows:

| Task | OOF accuracy, unshuffled (cv=5) | OOF accuracy, shuffled (seed 42) | OOF ECE, unshuffled | OOF ECE, shuffled |
|---|---|---|---|---|
| A1 | 0.6701 | 0.9321 | 0.2935 | 0.0509 |
| A2-VPN | 0.7897 | 0.9048 | 0.1522 | 0.0616 |
| A2-NonVPN | 0.8841 | 0.9566 | 0.0956 | 0.0350 |
| B | 0.7486 | 0.8738 | 0.1273 | 0.0420 |

(The shuffled OOF accuracies equal the headline source runs' CV mean accuracy exactly, as they
use the same folds, and are within 0.009 of their validation accuracy.)

Correction: the calibrator uses `cv=StratifiedKFold(5, shuffle=True, random_state=42)`, the same
folds as every other cross-validation in the project (`train.py`), via
`calibration.calibration_folds`; the logged param `calibration.method` names it. Everything else
above is unchanged: isotonic only, `ensemble=False`, fitted on training rows only, the predicted
class is the uncalibrated one, the adoption rule (uncalibrated validation ECE > 0.05 and isotonic
ECE lower) and thresholds (a)-(c) are not moved. All 4 E15 runs, A1 included, run again from the
corrected commit; only those runs count.

Side finding (inference, not proof): holding out contiguous blocks of the file costs 0.07-0.26 of
out-of-fold accuracy, so neighbouring rows in the files, probably flows of the same capture,
resemble each other more than random rows do. A random split puts such neighbours on both sides,
so random-split scores may be optimistic for traffic from new captures. This is the session-leakage
risk E11 could not test (no session IDs, E00); it goes to the report's Limitations. The file order is
not a session ID, so this is not a session-aware evaluation and no score is changed by it.

**2. Bootstrap: 10,000 stratified paired resamples per task, seed 42** (replaces part 1's 1,000).
- Stratified: each resample draws, within each true class, as many test rows as that class has,
  with replacement, so every resample keeps the test set's class counts (the test split is
  itself stratified; smallest test class 36 rows, MAIL in A2-NonVPN and B). The intervals are
  therefore conditional on the observed class counts; this is stated with the results.
- Paired: one set of resample indices per task (numpy `default_rng(42)`), used for every model of
  that task, for the intervals and for the tests.
- Intervals: 95% percentile intervals (2.5th and 97.5th percentiles) for macro F1, accuracy and
  each difference d.
- Why 10,000 and not 1,000: with B resamples the smallest possible two-sided p is 2 / (B + 1).
  For B = 1,000 that is 0.0020, above Holm's first threshold 0.05 / 26 = 0.0019, so no test could
  ever reject. For B = 10,000 it is 0.0002.
- All intervals and tests are computed afterwards from each run's saved test predictions
  (item 4), not by refitting models.

**3. Calibration (E15) is settled on validation before the test set is opened.**
- Data: the 4 headline configs fitted on the training rows only (they reproduce the saved source
  runs exactly); ECE measured on the validation rows.
- ECE: confidence = the probability the model gives its predicted class; 15 equal-width bins on
  [0, 1]; ECE = sum over bins of (rows in bin / all rows) x |accuracy in bin - mean confidence in
  bin|; plus a reliability diagram.
- Calibrator: only isotonic, `CalibratedClassifierCV(method="isotonic", cv=5, ensemble=False)`,
  fitted on the training rows. `ensemble=False` fits the base model once on all the rows it is
  given and learns the isotonic mapping from 5-fold out-of-fold predictions, so the base model is
  the same single model as the uncalibrated one, and no validation label is used to fit the
  mapping. No other calibration method is tried, on validation or test.
- Adoption rule per task: calibration is adopted if the uncalibrated validation ECE is above 0.05
  AND the calibrated validation ECE is lower than the uncalibrated one. Decided per task and
  recorded in E15.md before the test set is opened.
- Calibration changes only the reported confidence, never the predicted class: the predicted
  class is always the uncalibrated model's argmax, and the confidence reported (predict.py, demo)
  is the calibrated probability of THAT class. Multiclass isotonic calibration can reorder class
  probabilities, so the argmax of the calibrated probabilities is never used as the prediction.
  Test macro F1, accuracy and all tests above are therefore unaffected by calibration.
- Final model: where adopted, the same calibrator is fitted on train + validation (base model =
  the train + validation retrain, the mapping from 5-fold out-of-fold predictions). The
  validation ECE is evidence for the decision only, not an independent measure of the final
  model's calibration; the test ECE (computed with the probabilities actually used: calibrated
  where adopted, else the original) is the one independent measure, reported once, with the
  uncalibrated test ECE beside it for reference.

**4. Rehearsal before the official test runs, and crash rules.**
- Rehearsal: the new run kind for the final runs is first run in a scratch clone with its own
  MLflow store (runner name other than utsav-s-r), with each model fitted on the training rows
  and scored on the validation rows in place of the test rows; a unit test shows that this mode

- Each official run saves its test predictions (row id, true label, predicted label, class
  probabilities) as an MLflow artifact. The official runs go in one batch, from committed and
  pushed code, after the rehearsal passes.
- Crash before a run's test predictions are written: rerun that run with the identical committed
  config and code (deterministic, seed 42).
- Crash after predictions or metrics were written: do not refit; compute what is missing from
  the saved predictions.
- Any rerun after a test score was seen: allowed only as a technical rerun with identical code,

- Every attempt, failed or not, stays in MLflow and is listed in part 2.

### E08 — Class balancing ladder on the current best model (2026-10-28, utsav-s-r)

Hypothesis: three of the four tasks are imbalanced (largest to smallest class at 15 s, from
`data/manifest.json`: A1 1.08:1, A2-VPN 5.79:1, A2-NonVPN 11.85:1, B 11.85:1). A model trained
without balancing favours the large classes, so the small ones lose recall, and macro F1 weights
every class the same. Balancing the training rows (class weights, random oversampling or SMOTE)
should raise the F1 of the weak small classes and with it macro F1 in A2-VPN, A2-NonVPN and B.
A1 is almost balanced, so balancing should change little there.

- (a) the best balancing step beats "none" by at least 0.01 in at least 2 of the 3 imbalanced
  tasks (A2-VPN, A2-NonVPN, B);
- (b) in A1, no step changes validation macro F1 by more than 0.01 either way;
- (c) in at least 2 of the 3 imbalanced tasks, the best balancing step raises the F1 of the

The steps (`balance` in the config, `src/blindspy/models.py` `build_model`; logged as param

resamples only the rows it is fitted on: each CV training fold and then the training set. CV
test folds, validation and test rows are never resampled or seen. Known limit, kept on purpose

which the large-valued timing columns dominate; scaling first would be a second change.

### E07 — Hyperparameter tuning with Optuna, same budget for every model (2026-10-28, utsav-s-r)

Hypothesis: E05 and E06 ran with default settings. Tuning the main settings (number of trees,
depth, learning rate, row and column sampling, leaf size) to these data should improve each
model a little, since defaults are general-purpose. The tuned KNN (number of neighbours,
distance weighting, metric) gets the same budget so that no model wins only because it was
tuned more (Isnan et al. list untuned baselines as a weakness). Tuning should not change the
ranking: the tree ensembles stay ahead of KNN.

Each part gets its own verdict.

Winner rule (decided 28 Oct, written here before running): a model whose 15 s validation macro
F1 beats that task's current best by at least 0.03 is a winner and is rerun at 30, 60 and
120 s with its 15 s settings, tuned hyperparameters included (nothing is re-tuned per timeout:
that would be a different, 4 times costlier experiment). Why 0.03: it is above the largest
Phase 2 CV standard deviation (0.025), so a smaller gain could be noise from the split; a fixed
number set before running keeps the choice honest and repeatable. The current best is the
highest 15 s validation macro F1 whatever the margin; the 0.03 only decides the reruns.

Change vs the untuned runs (one change: the hyperparameters, chosen by search). Scope (decided

- A2-VPN, A2-NonVPN, B: XGBoost, LightGBM, KNN.
That is 12 searches. Each search: Optuna `TPESampler(seed=42)`, 50 trials run one after another
(parallel TPE trials are not reproducible), every trial scored by the mean macro F1 of 5-fold
stratified CV on the training rows (the folds of one trial run in parallel, each model on one
thread). Validation and test rows are never seen by the search. The best trial's settings are
then trained on all training rows and scored on validation exactly like any other run; that
model is saved. Trials keep settings and scores only (no model file); they are nested MLflow
runs tagged `trial=True`, protocol `optuna_trial`, and are kept out of the result tables.

- XGBoost: n_estimators 100-1000; learning_rate 0.01-0.3 (log scale); max_depth 3-12;

- LightGBM: n_estimators 100-1000; learning_rate 0.01-0.3 (log scale); num_leaves 15-255;

- KNN (signed log + StandardScaler): n_neighbors 1-50; weights uniform or distance; metric
  euclidean or manhattan.
"No limit" and "fraction" are encoded as an extra categorical choice (`max_depth_limited`,
`max_features_kind`), so TPE samples them like any other setting (`src/blindspy/tuning.py`).

### E04 — KNN with a signed log transform: StandardScaler vs RobustScaler (2026-10-28, utsav-s-r)

Hypothesis: KNN classifies by distance, so on standard-scaled raw features a few very large
timing values (microseconds up to about 1.2e8, E00) dominate every distance. A signed log
sign(x) * log1p(|x|) before scaling compresses those tails, so the distance reflects the shape
of the whole flow and KNN (k = 5, as in E03) scores higher. After the log the columns are much
less heavy-tailed, so StandardScaler and RobustScaler should then give similar results.

Threshold (set before running, never moved afterwards), at 15 s, against E03 KNN (k = 5,
StandardScaler, no log; validation macro F1 A1 0.813, A2-VPN 0.774, A2-NonVPN 0.773, B 0.660,

- (a) the better of the two E04 variants beats E03 KNN validation macro F1 by at least 0.02 in
  at least 3 of the 4 tasks;
- (b) the two E04 variants are within 0.02 of each other in at least 3 of the 4 tasks.
Each part gets its own verdict.

Winner rule (decided 28 Oct, written here before running): a model whose 15 s validation macro
F1 beats that task's current best by at least 0.03 is a winner and is rerun at 30, 60 and
120 s with its 15 s settings. Why 0.03: it is above the largest Phase 2 CV standard deviation
(0.025), so a smaller gain could be noise from the split; a fixed number set before running
keeps the choice honest and repeatable. The current best at 15 s is the E02 tree (A1 0.890,
A2-VPN 0.825, A2-NonVPN 0.829, B 0.759). The current best is the highest 15 s validation macro
F1 whatever the margin; the 0.03 only decides the reruns.

What E07 takes from this: the KNN that E07 tunes uses, per task, whichever of the E03 and E04
preprocessings has the higher 15 s validation macro F1.

Change vs E03 (one change: the preprocessing): model `knn_log_standard` = Pipeline(signed log,
`StandardScaler`, `KNeighborsClassifier(n_neighbors=5)`) and `knn_log_robust` = Pipeline(signed
log, `RobustScaler`, same KNN). The signed log is `src/blindspy/features.py` (a fixed formula
inside the pipeline; nothing learned from data; data v1 unchanged). Why the signed log and not
plain log1p: log1p(-1) is minus infinity, and the features hold -1 "not measurable" codes and
586 negative min_flowiat values (E00). The signed log is defined everywhere, keeps the order of
values and keeps -1 apart from 0. Not chosen: shifting each column so its minimum is 0 before the
log (a shift learned from training data, different per column, and -1 merges into small values);
logging only the non-negative columns (inconsistent, leaves large values uncompressed);
replacing -1 by 0 plus flag columns (changes the feature set, so E04 would change two things).

(`scripts/make_configs.py`). Protocol as E03: 5-fold stratified CV on train, fit on train,

### E01 — Majority-class baseline, all tasks and timeouts (2026-10-28, utsav-s-r)

Hypothesis: a model that always predicts the largest training class sets the floor every
model must beat. Its validation accuracy equals that class's share p of the validation set,
and its macro F1 equals 2p / ((1 + p) k) for k classes (F1 of the predicted class is
2p / (1 + p); every other class scores 0). The stratified split keeps p the same in train and
validation, so CV and validation should agree.

Threshold (set before running, never moved afterwards): supported if, in all 16 configs
(4 tasks x 4 timeouts), |validation accuracy - p| <= 0.001 and
|validation macro F1 - 2p / ((1 + p) k)| <= 0.001. Any miss means a bug in the pipeline or
the metrics, and the runs are not used until it is fixed.

Change: none (first baseline). Model `majority` = `DummyClassifier(strategy="most_frequent",
random_state=42)`. Configs: `configs/experiments/E01_majority_<task>_<timeout>s.yaml`

train, score on validation (test not used). Data version v1.

tag v0.1-baseline). Numbers below come from `reports/baseline_tables.md` (generated by
