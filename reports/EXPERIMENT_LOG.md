### E08 — Class balancing ladder on the current best model (2026-10-28, utsav-s-r)

Hypothesis: three of the four tasks are imbalanced (largest to smallest class at 15 s, from
`data/manifest.json`: A1 1.08:1, A2-VPN 5.79:1, A2-NonVPN 11.85:1, B 11.85:1). A model trained
without balancing favours the large classes, so the small ones lose recall, and macro F1 weights
every class the same. Balancing the training rows (class weights, random oversampling or SMOTE)
should raise the F1 of the weak small classes and with it macro F1 in A2-VPN, A2-NonVPN and B.
A1 is almost balanced, so balancing should change little there.

Threshold (set before running, never moved afterwards), validation macro F1 at 15 s against the
current best after E07 (the "none" step; reference values from `reports/phase3_tables.md`, table
"Current best at 15 s after E07": A1 0.9271, A2-VPN 0.8768, A2-NonVPN 0.9028, B 0.8428):
- (a) the best balancing step beats "none" by at least 0.01 in at least 2 of the 3 imbalanced
  tasks (A2-VPN, A2-NonVPN, B);
- (b) in A1, no step changes validation macro F1 by more than 0.01 either way;
- (c) in at least 2 of the 3 imbalanced tasks, the best balancing step raises the F1 of the
  class that is weakest without balancing (A2-VPN VPN-CHAT 0.7343, A2-NonVPN STREAMING 0.8095,
  B VPN-MAIL 0.6496, from the runs' per-class F1).
Each part gets its own verdict.

Ladder and stop rule (plan: "none -> class_weight -> random oversampling -> SMOTE; stop early if
a step doesn't help"), per task, written here before running: step 0 "none" is the current best
run itself (not rerun). A step helps if its 15 s validation macro F1 is higher than that of every
earlier step in that task (any margin, the same rule as "current best"). The next step runs only
if this one helped; otherwise that task's ladder stops. Steps therefore run in rounds: round 1 =
class_weight in all 4 tasks; the next round only where the previous step helped. The order is
the plan's "simpler first" order (no balancing < class_weight < oversampling < SMOTE).

Winner rule (decided 28 Oct, written here before running): a model whose 15 s validation macro
F1 beats that task's current best by at least 0.03 is a winner and is rerun at 30, 60 and
120 s with its 15 s settings, balancing included (nothing is re-tuned per timeout: that would be
a different, 4 times costlier experiment). Why 0.03: it is above the largest Phase 2 CV standard
deviation (0.025), so a smaller gain could be noise from the split; a fixed number set before
running keeps the choice honest and repeatable. The current best is the highest 15 s validation
macro F1 whatever the margin; the 0.03 only decides the reruns.

Change vs the current best (one change: class balancing). Each task keeps the model type and
every setting of its current best after E07, copied from the logged params of that run (not
typed; `results.run_settings`, used by `scripts/make_configs.py`; each config names it in
`builds_on`, also logged as a param):
- A1: E06 XGBoost, defaults (E06-xgb-A1-15s);
- A2-VPN: E07 LightGBM, tuned (E07-lgbm-A2-VPN-15s);
- A2-NonVPN: E07 LightGBM, tuned (E07-lgbm-A2-NonVPN-15s);
- B: E07 XGBoost, tuned (E07-xgb-B-15s).
Check before running: each base rebuilt from the copied settings, without balancing, fitted on
the training rows reproduces its logged validation macro F1 exactly (4 of 4).

The steps (`balance` in the config, `src/blindspy/models.py` `build_model`; logged as param
`class_balancing`):
- class_weight: `class_weight="balanced"` (weight of a class = rows / (classes x rows of that
  class)). LightGBM has it natively; XGBoost has no class_weight, so the XGBoost wrapper turns it
  into per-row sample weights with `compute_sample_weight("balanced")` (decided 28 Oct).
- oversample: `RandomOverSampler(random_state=42)` repeats rows of the smaller classes until every
  class has as many rows as the largest.
- smote: `SMOTE(k_neighbors=5, random_state=42)` creates new rows between a row and one of its 5
  nearest neighbours of the same class until every class matches the largest. k = 5 is safe: the
  smallest training class is 53 rows (MAIL, A2-NonVPN 30 s), about 42 per CV training fold.
The two resampling steps sit right before the model in an imbalanced-learn Pipeline, which
resamples only the rows it is fitted on: each CV training fold and then the training set. CV
test folds, validation and test rows are never resampled or seen. Known limit, kept on purpose
(one change per experiment): SMOTE finds neighbours by Euclidean distance on the raw features,
which the large-valued timing columns dominate; scaling first would be a second change.

Protocol as E04-E07: 5-fold stratified CV on train, fit on train, score on validation; test set
untouched. Models saved with joblib compression level 3. Data version v1.

New model type (imbalanced-learn pipeline): the first resampling run's logged fields are checked
by query before the rest of its round.

### E07 — Hyperparameter tuning with Optuna, same budget for every model (2026-10-28, utsav-s-r)

Hypothesis: E05 and E06 ran with default settings. Tuning the main settings (number of trees,
depth, learning rate, row and column sampling, leaf size) to these data should improve each
model a little, since defaults are general-purpose. The tuned KNN (number of neighbours,
distance weighting, metric) gets the same budget so that no model wins only because it was
tuned more (Isnan et al. list untuned baselines as a weakness). Tuning should not change the
ranking: the tree ensembles stay ahead of KNN.

Threshold (set before running, never moved afterwards), validation macro F1 at 15 s; reference
values from `reports/phase3_tables.md`:
- (a) in at least 8 of the 12 searches, the tuned model scores above its own untuned version
  (E06 XGBoost, E05 Random Forest, E06 LightGBM, E04 signed-log KNN with k = 5);
- (b) the best E07 model per task beats the current best after E06, XGBoost with defaults
  (A1 0.9271, A2-VPN 0.8758, A2-NonVPN 0.9015, B 0.8303), by at least 0.01 in at least 2 of
  the 4 tasks;
- (c) the tuned KNN stays below the best tuned tree ensemble in all 4 tasks.
Each part gets its own verdict.

Winner rule (decided 28 Oct, written here before running): a model whose 15 s validation macro
F1 beats that task's current best by at least 0.03 is a winner and is rerun at 30, 60 and
120 s with its 15 s settings, tuned hyperparameters included (nothing is re-tuned per timeout:
that would be a different, 4 times costlier experiment). Why 0.03: it is above the largest
Phase 2 CV standard deviation (0.025), so a smaller gain could be noise from the split; a fixed
number set before running keeps the choice honest and repeatable. The current best is the
highest 15 s validation macro F1 whatever the margin; the 0.03 only decides the reruns.

Change vs the untuned runs (one change: the hyperparameters, chosen by search). Scope (decided
28 Oct; table "E07 scope" in `reports/phase3_tables.md`): per task the best 2 of Random Forest,
XGBoost and LightGBM by 15 s validation macro F1, plus KNN with the better of the E03/E04
preprocessing, which is the signed log + StandardScaler in every task:
- A1: XGBoost, Random Forest, KNN;
- A2-VPN, A2-NonVPN, B: XGBoost, LightGBM, KNN.
That is 12 searches. Each search: Optuna `TPESampler(seed=42)`, 50 trials run one after another
(parallel TPE trials are not reproducible), every trial scored by the mean macro F1 of 5-fold
stratified CV on the training rows (the folds of one trial run in parallel, each model on one
thread). Validation and test rows are never seen by the search. The best trial's settings are
then trained on all training rows and scored on validation exactly like any other run; that
model is saved. Trials keep settings and scores only (no model file); they are nested MLflow
runs tagged `trial=True`, protocol `optuna_trial`, and are kept out of the result tables.

Search ranges (fixed in the plan, written into `scripts/make_configs.py` and every

- XGBoost: n_estimators 100-1000; learning_rate 0.01-0.3 (log scale); max_depth 3-12;
  subsample 0.5-1.0; colsample_bytree 0.5-1.0; min_child_weight 1-50.
- LightGBM: n_estimators 100-1000; learning_rate 0.01-0.3 (log scale); num_leaves 15-255;

  `subsample` when `subsample_freq` > 0 (its default is 0), so its searches fix
  `subsample_freq=1` (sample rows anew for every tree); otherwise that range would do nothing.
- KNN (signed log + StandardScaler): n_neighbors 1-50; weights uniform or distance; metric
  euclidean or manhattan.
"No limit" and "fraction" are encoded as an extra categorical choice (`max_depth_limited`,
`max_features_kind`), so TPE samples them like any other setting (`src/blindspy/tuning.py`).

### E05 — Random Forest, 300 trees (2026-10-28, utsav-s-r)

rows. A Random Forest averages 300 such trees, each grown on a bootstrap sample with a random
subset of features at every split, which lowers that variance. It should clearly beat the
single tree, and since the current best (signed-log KNN, E04) is only 0.006-0.038 above the
tree, the forest should also pass it in at least half of the tasks.

  at least 0.03 in at least 3 of the 4 tasks;
- (b) the forest beats the current best, E04-knn_log_standard (A1 0.9048, A2-VPN 0.8544,
  A2-NonVPN 0.8670, B 0.7644), in at least 2 of the 4 tasks (any margin).
Each part gets its own verdict.

F1 beats that task's current best by at least 0.03 is a winner and is rerun at 30, 60 and
120 s with its 15 s settings. Why 0.03: it is above the largest Phase 2 CV standard deviation
(0.025), so a smaller gain could be noise from the split; a fixed number set before running

### E04 — KNN with a signed log transform: StandardScaler vs RobustScaler (2026-10-28, utsav-s-r)

Hypothesis: KNN classifies by distance, so on standard-scaled raw features a few very large
timing values (microseconds up to about 1.2e8, E00) dominate every distance. A signed log
sign(x) * log1p(|x|) before scaling compresses those tails, so the distance reflects the shape
of the whole flow and KNN (k = 5, as in E03) scores higher. After the log the columns are much
less heavy-tailed, so StandardScaler and RobustScaler should then give similar results.

Threshold (set before running, never moved afterwards), at 15 s, against E03 KNN (k = 5,
StandardScaler, no log; validation macro F1 A1 0.813, A2-VPN 0.774, A2-NonVPN 0.773, B 0.660,
from `reports/baseline_tables.md`):
- (a) the better of the two E04 variants beats E03 KNN validation macro F1 by at least 0.02 in
  at least 3 of the 4 tasks;
- (b) the two E04 variants are within 0.02 of each other in at least 3 of the 4 tasks.
Each part gets its own verdict.

Winner rule (decided 28 Oct, written here before running): a model whose 15 s validation macro
F1 beats that task's current best by at least 0.03 is a winner and is rerun at 30, 60 and
120 s with its 15 s settings. Why 0.03: it is above the largest Phase 2 CV standard deviation
(0.025), so a smaller gain could be noise from the split; a fixed number set before running
keeps the choice honest and repeatable. The current best at 15 s is the E02 tree (A1 0.890,
A2-VPN 0.825, A2-NonVPN 0.829, B 0.759). The current best is the highest 15 s validation macro
F1 whatever the margin; the 0.03 only decides the reruns.

What E07 takes from this: the KNN that E07 tunes uses, per task, whichever of the E03 and E04
preprocessings has the higher 15 s validation macro F1.

Change vs E03 (one change: the preprocessing): model `knn_log_standard` = Pipeline(signed log,
`StandardScaler`, `KNeighborsClassifier(n_neighbors=5)`) and `knn_log_robust` = Pipeline(signed
log, `RobustScaler`, same KNN). The signed log is `src/blindspy/features.py` (a fixed formula
inside the pipeline; nothing learned from data; data v1 unchanged). Why the signed log and not
plain log1p: log1p(-1) is minus infinity, and the features hold -1 "not measurable" codes and
586 negative min_flowiat values (E00). The signed log is defined everywhere, keeps the order of
values and keeps -1 apart from 0. Not chosen: shifting each column so its minimum is 0 before the
log (a shift learned from training data, different per column, and -1 merges into small values);
logging only the non-negative columns (inconsistent, leaves large values uncompressed);
replacing -1 by 0 plus flag columns (changes the feature set, so E04 would change two things).

(`scripts/make_configs.py`). Protocol as E03: 5-fold stratified CV on train, fit on train,

### E01 — Majority-class baseline, all tasks and timeouts (2026-10-28, utsav-s-r)

Hypothesis: a model that always predicts the largest training class sets the floor every
model must beat. Its validation accuracy equals that class's share p of the validation set,
and its macro F1 equals 2p / ((1 + p) k) for k classes (F1 of the predicted class is
2p / (1 + p); every other class scores 0). The stratified split keeps p the same in train and
validation, so CV and validation should agree.

Threshold (set before running, never moved afterwards): supported if, in all 16 configs
(4 tasks x 4 timeouts), |validation accuracy - p| <= 0.001 and
|validation macro F1 - 2p / ((1 + p) k)| <= 0.001. Any miss means a bug in the pipeline or
the metrics, and the runs are not used until it is fixed.

Change: none (first baseline). Model `majority` = `DummyClassifier(strategy="most_frequent",
random_state=42)`. Configs: `configs/experiments/E01_majority_<task>_<timeout>s.yaml`
(generated by `scripts/make_configs.py`). Protocol: 5-fold stratified CV on train, fit on
train, score on validation (test not used). Data version v1.

Result: 80 baseline runs, all FINISHED, from dev commit 1817c5a (committed and pushed;
tag v0.1-baseline). Numbers below come from `reports/baseline_tables.md` (generated by
`scripts/results_tables.py` from `reports/history.csv`).

- All 16 configs match the arithmetic to 4 decimals (table "E01 check"): e.g. A1 15 s, largest
  class VPN, p = 0.5185, validation accuracy 0.5185, expected and measured macro F1 0.3414; B 15 s,
  largest class VOIP, p = 0.1560, macro F1 0.0193.
- The floor in validation macro F1: A1 0.337-0.358, A2-VPN 0.060-0.093, A2-NonVPN 0.067-0.096,
  B 0.019-0.030. Balanced accuracy is exactly 1/k (0.500, 0.143, 0.071) and A1 ROC-AUC 0.5.

### E00 — Data findings and data v1 (2026-10-27, utsav-s-r)

Hypothesis (from the plan, written before the check): the ARFF `@ATTRIBUTE` names may not match
the data order. In A1 15 s row 1, `total_fiat` = 16 and `total_biat` = 4 in a 9.37 s flow, which
looks wrong; the paper's Table 2 and the authors' 2016 poster list fiat/biat as min, mean, max,
std, with no totals. Candidates: `total_*` are packet counts, `std_*`, or something else.

Threshold: no numeric threshold was written before the check. Decision rule used: a name list
is accepted for a file when every structural identity (min <= mean <= max per group, 0 <= std <=
max - min, gaps x (packets - 1) = duration) holds on 100% of applicable rows, allowing for the
source's rounding. A list is rejected when the identities fail on most rows.

(`src/blindspy/checks.py`), `scripts/prepare_data.py` and `src/blindspy/splits.py`, then data
