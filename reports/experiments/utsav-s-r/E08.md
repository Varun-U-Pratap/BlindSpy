### E08 — Class balancing ladder on the current best model (2026-10-28, utsav-s-r)

Hypothesis: three of the four tasks are imbalanced (largest to smallest class at 15 s, from
`data/manifest.json`: A1 1.08:1, A2-VPN 5.79:1, A2-NonVPN 11.85:1, B 11.85:1). A model trained
without balancing favours the large classes, so the small ones lose recall, and macro F1 weights
every class the same. Balancing the training rows (class weights, random oversampling or SMOTE)
should raise the F1 of the weak small classes and with it macro F1 in A2-VPN, A2-NonVPN and B.
A1 is almost balanced, so balancing should change little there.

Threshold (set before running, never moved afterwards), validation macro F1 at 15 s against the
current best after E07 (the "none" step; reference values from `reports/phase3_tables.md`, table
"Current best at 15 s after E07": A1 0.9271, A2-VPN 0.8768, A2-NonVPN 0.9028, B 0.8428):
- (a) the best balancing step beats "none" by at least 0.01 in at least 2 of the 3 imbalanced
  tasks (A2-VPN, A2-NonVPN, B);
- (b) in A1, no step changes validation macro F1 by more than 0.01 either way;
- (c) in at least 2 of the 3 imbalanced tasks, the best balancing step raises the F1 of the
  class that is weakest without balancing (A2-VPN VPN-CHAT 0.7343, A2-NonVPN STREAMING 0.8095,
  B VPN-MAIL 0.6496, from the runs' per-class F1).
Each part gets its own verdict.

Ladder and stop rule (plan: "none -> class_weight -> random oversampling -> SMOTE; stop early if
a step doesn't help"), per task, written here before running: step 0 "none" is the current best
run itself (not rerun). A step helps if its 15 s validation macro F1 is higher than that of every
earlier step in that task (any margin, the same rule as "current best"). The next step runs only
if this one helped; otherwise that task's ladder stops. Steps therefore run in rounds: round 1 =
class_weight in all 4 tasks; the next round only where the previous step helped. The order is
the plan's "simpler first" order (no balancing < class_weight < oversampling < SMOTE).

Winner rule (decided 28 Oct, written here before running): a model whose 15 s validation macro
F1 beats that task's current best by at least 0.03 is a winner and is rerun at 30, 60 and
120 s with its 15 s settings, balancing included (nothing is re-tuned per timeout: that would be
a different, 4 times costlier experiment). Why 0.03: it is above the largest Phase 2 CV standard
deviation (0.025), so a smaller gain could be noise from the split; a fixed number set before
running keeps the choice honest and repeatable. The current best is the highest 15 s validation
macro F1 whatever the margin; the 0.03 only decides the reruns.

Change vs the current best (one change: class balancing). Each task keeps the model type and
every setting of its current best after E07, copied from the logged params of that run (not
typed; `results.run_settings`, used by `scripts/make_configs.py`; each config names it in
`builds_on`, also logged as a param):
- A1: E06 XGBoost, defaults (E06-xgb-A1-15s);
- A2-VPN: E07 LightGBM, tuned (E07-lgbm-A2-VPN-15s);
- A2-NonVPN: E07 LightGBM, tuned (E07-lgbm-A2-NonVPN-15s);
- B: E07 XGBoost, tuned (E07-xgb-B-15s).

The steps (`balance` in the config, `src/blindspy/models.py` `build_model`; logged as param
`class_balancing`):
- class_weight: `class_weight="balanced"` (weight of a class = rows / (classes x rows of that
  class)). LightGBM has it natively; XGBoost has no class_weight, so the XGBoost wrapper turns it
  into per-row sample weights with `compute_sample_weight("balanced")` (decided 28 Oct).
- oversample: `RandomOverSampler(random_state=42)` repeats rows of the smaller classes until every
  class has as many rows as the largest.
- smote: `SMOTE(k_neighbors=5, random_state=42)` creates new rows between a row and one of its 5
  nearest neighbours of the same class until every class matches the largest. k = 5 is safe: the
  smallest training class is 53 rows (MAIL, A2-NonVPN 30 s), about 42 per CV training fold.
The two resampling steps sit right before the model in an imbalanced-learn Pipeline, which
resamples only the rows it is fitted on: each CV training fold and then the training set. CV
test folds, validation and test rows are never resampled or seen. Known limit, kept on purpose
(one change per experiment): SMOTE finds neighbours by Euclidean distance on the raw features,
which the large-valued timing columns dominate; scaling first would be a second change.

Protocol as E04-E07: 5-fold stratified CV on train, fit on train, score on validation; test set
untouched. Models saved with joblib compression level 3. Data version v1.

New model type (imbalanced-learn pipeline): the first resampling run's logged fields are checked
by query before the rest of its round.

Result: 7 runs in 3 rounds, all FINISHED, committed and pushed, data v1: round 1 (class_weight,
4 tasks) from dev 38ccc65, round 2 (oversample, A2-VPN and A2-NonVPN) from 4ecf982, round 3
(SMOTE, A2-NonVPN) from 2b9a93c. Each round's configs and the previous round's results were

- A2-VPN: oversampling scored 0.882972 against 0.882982 for class weights (exact values from the
  store), 0.00001 lower. By the rule set before running (any margin) it did not help and the
  ladder stopped; in practice the two are equal.
- Gains are small: the best step per task is +0.0062 (A2-VPN, class_weight), +0.0047 (A2-NonVPN,
  oversample) and -0.0064 (B, class_weight); in A1 class weights cost 0.0034.
- The weak small classes gain a little where balancing helps: VPN-CHAT F1 0.7343 -> 0.7463
  (A2-VPN), STREAMING 0.8095 -> 0.8372 (A2-NonVPN; its recall 0.761 -> 0.806). In B, class weights
  raise VPN-MAIL recall 0.585 -> 0.600 but lose more in precision, so its F1 falls 0.6496 ->
  0.6290 and macro F1 falls too.
- No winner (largest gain over the best before E08: +0.0062), so nothing is rerun at 30, 60 or
  120 s. New current best at 15 s (table "Current best at 15 s after E08"): A2-VPN
  E08-lgbm_class_weight 0.8830, A2-NonVPN E08-lgbm_oversample 0.9075; A1 (E06 XGBoost 0.9271) and
  B (E07 XGBoost 0.8428) unchanged. Both new bests are within 0.03 of the unbalanced model, so
  the final choice treats them as ties (tie rule: no balancing is simpler).
- Cost: class weights change training time little (A2-VPN 12.8 s, as without); resampling adds
  rows, so it costs more: A2-NonVPN train 5.1 s (oversample) and 6.4 s (SMOTE) against 3.4 s
  (class weights). SMOTE also grows deeper trees (mean depth 8.6 against 6.3-6.6; 242,784 nodes)
  and predicts slowest (421 ms per 1,000 flows against 284-326). Model files 0.12-27.0 MiB as saved.
- 5-fold CV agrees with validation (|CV - val| <= 0.028; CV std 0.0034-0.0094).

Verdict: (a) not supported (the best step beats "none" by >= 0.01 in 0 of the 3 imbalanced
tasks: A2-VPN +0.0062, A2-NonVPN +0.0047, B -0.0064). (b) supported (A1: the one step run changed
macro F1 by -0.0034, within 0.01). (c) supported (the best step raises the F1 of the class that
is weakest without balancing in 2 of 3 tasks: A2-VPN +0.012, A2-NonVPN +0.0277; B -0.0206).

Decision: balancing barely matters for these models (all changes within +-0.0064). That suggests
the remaining errors of the weak classes (VPN-CHAT, STREAMING, VPN-MAIL) come from flows that
look like those of other classes rather than from too few training rows; E08 does not test this. Current best after E08 per task: A1 E06 XGBoost
(defaults), A2-VPN E08 LightGBM tuned + class weights, A2-NonVPN E08 LightGBM tuned +
oversampling, B E07 XGBoost tuned. E10 (task B, direct vs two-step) uses the current best B model
type and settings, E07 XGBoost tuned without balancing. Next: E10.
