### E10 — Task B: one 14-class model vs two steps (VPN / non-VPN, then 7 classes) (2026-10-28, utsav-s-r)

Hypothesis: task B mixes two questions, "is this flow VPN?" and "which application type?". A
two-step model asks them in turn: a VPN / non-VPN model routes each flow to one of two 7-class
models that each see only their own group. It could help if a model trained only on the VPN
question gets the group right more often than the direct model does, and if each 7-class model
separates types better without the other group's classes. It cannot recover from a wrong first
step: such a flow lands in the wrong group and is always wrong. The direct model (current best
B after E08, E07 XGBoost tuned) already gets the group right for most flows: computed before
running from its validation confusion matrix (`results.vpn_group_errors`), 180 of its 327 errors
on 2,711 validation rows cross the VPN / non-VPN line (group accuracy 0.9336; 55.05% of its
errors), 147 are the wrong type within the right group. Expected: the two structures score about
the same.

Threshold (set before running, never moved afterwards), on the same B validation rows at 15 s,
against the direct model E07-xgb-B-15s (14-class validation macro F1 0.8428, from
`reports/phase3_tables.md`, table "Current best at 15 s after E08"):
- (a) the two-step 14-class validation macro F1 is within 0.01 of the direct model (|difference|
  <= 0.01);
- (b) the two-step's first step makes fewer group errors than the direct model's 180;
- (c) more than half of the two-step's errors come from a wrong first step.
Each part gets its own verdict.

Winner rule (decided 28 Oct, written here before running): a model whose 15 s validation macro
F1 beats that task's current best by at least 0.03 is a winner and is rerun at 30, 60 and
120 s with its 15 s settings (nothing is re-tuned per timeout: that would be a different, 4
times costlier experiment). Why 0.03: it is above the largest Phase 2 CV standard deviation
(0.025), so a smaller gain could be noise from the split; a fixed number set before running
keeps the choice honest and repeatable. The current best is the highest 15 s validation macro
F1 whatever the margin; the 0.03 only decides the reruns. Tie rule for the final choice: direct
is simpler than two-step.

Change vs the current best (one change: the structure). Every model in the two-step uses the
current best B model type and settings, E07 XGBoost tuned (505 rounds, learning rate 0.101,
depth 6, row sampling 0.915, column sampling 0.895, min_child_weight 2, seed 42, one thread),
copied from the logged params of E07-xgb-B-15s (`results.run_settings`, `builds_on` in the config
and as a param). The direct 14-class model is that run itself (not rerun). Model
`xgb_two_step` (`src/blindspy/models.py`, `TwoStep`):
- step 1: the XGBoost model on the B training rows with label VPN / non-VPN, taken from the B
  label (the 7 classes starting with "VPN-" are VPN). Not the A1 split (decided 28 Oct): A1 and
  B hold the same flows with different splits, so an A1-trained model has seen B validation
  flows;
- step 2: two XGBoost 7-class models, one on the B training rows whose true label is VPN, one on
  the rest. Same column layout as B (std_fiat / std_biat, E00); the A2 files are not used (they
  hold total_fiat / total_biat);
- prediction: the step-1 group decides which 7-class model answers. Class probabilities are the
  routed model's; the other group's classes get 0, so the most likely class is exactly the routed
  model's prediction.
In 5-fold CV all three models are trained on each training fold only. The number of errors from
a wrong first step = the validation errors that cross the VPN / non-VPN line (with hard routing
these are the same thing), read from the confusion matrix of each run (`results.vpn_group_errors`).

Config: `configs/experiments/E10_xgb_two_step_B_15s.yaml` (`scripts/make_configs.py`). Protocol
as E04-E08: 5-fold stratified CV on train, fit on train, score on validation (14-class macro F1);
test set untouched. Model saved with joblib compression level 3. Data version v1.

New model type (two-step): its run's logged fields are checked by query.
