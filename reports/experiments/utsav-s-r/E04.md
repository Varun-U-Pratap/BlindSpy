### E04 — KNN with a signed log transform: StandardScaler vs RobustScaler (2026-10-28, utsav-s-r)

Hypothesis: KNN classifies by distance, so on standard-scaled raw features a few very large
timing values (microseconds up to about 1.2e8, E00) dominate every distance. A signed log
sign(x) * log1p(|x|) before scaling compresses those tails, so the distance reflects the shape
of the whole flow and KNN (k = 5, as in E03) scores higher. After the log the columns are much
less heavy-tailed, so StandardScaler and RobustScaler should then give similar results.

Threshold (set before running, never moved afterwards), at 15 s, against E03 KNN (k = 5,
StandardScaler, no log; validation macro F1 A1 0.813, A2-VPN 0.774, A2-NonVPN 0.773, B 0.660,
from `reports/baseline_tables.md`):
- (a) the better of the two E04 variants beats E03 KNN validation macro F1 by at least 0.02 in
  at least 3 of the 4 tasks;
- (b) the two E04 variants are within 0.02 of each other in at least 3 of the 4 tasks.
Each part gets its own verdict.

Winner rule (decided 28 Oct, written here before running): a model whose 15 s validation macro
F1 beats that task's current best by at least 0.03 is a winner and is rerun at 30, 60 and
120 s with its 15 s settings. Why 0.03: it is above the largest Phase 2 CV standard deviation
(0.025), so a smaller gain could be noise from the split; a fixed number set before running
keeps the choice honest and repeatable. The current best at 15 s is the E02 tree (A1 0.890,
A2-VPN 0.825, A2-NonVPN 0.829, B 0.759). The current best is the highest 15 s validation macro
F1 whatever the margin; the 0.03 only decides the reruns.

What E07 takes from this: the KNN that E07 tunes uses, per task, whichever of the E03 and E04
preprocessings has the higher 15 s validation macro F1.

Change vs E03 (one change: the preprocessing): model `knn_log_standard` = Pipeline(signed log,
`StandardScaler`, `KNeighborsClassifier(n_neighbors=5)`) and `knn_log_robust` = Pipeline(signed
log, `RobustScaler`, same KNN). The signed log is `src/blindspy/features.py` (a fixed formula
inside the pipeline; nothing learned from data; data v1 unchanged). Why the signed log and not
plain log1p: log1p(-1) is minus infinity, and the features hold -1 "not measurable" codes and
586 negative min_flowiat values (E00). The signed log is defined everywhere, keeps the order of
values and keeps -1 apart from 0. Not chosen: shifting each column so its minimum is 0 before the
log (a shift learned from training data, different per column, and -1 merges into small values);
logging only the non-negative columns (inconsistent, leaves large values uncompressed);
replacing -1 by 0 plus flag columns (changes the feature set, so E04 would change two things).
Configs: `configs/experiments/E04_knn_log_{standard,robust}_<task>_15s.yaml`
(`scripts/make_configs.py`). Protocol as E03: 5-fold stratified CV on train, fit on train,
score on validation; test set untouched. Models saved with joblib compression level 3. Data
version v1.

Pilot: the first Phase 3 run (E04-knn_log_standard-A1-15s) is checked by hand in the MLflow UI
against the plan's tracking table, including the new Phase 3 items (compression level, both
model sizes, child-process RSS, n_jobs), before the other 7 runs.
